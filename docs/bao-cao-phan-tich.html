Cơ chế cách ly multi-tenant

Chuỗi xử lý mỗi request có token hợp lệ:

JwtFilter đọc claim "tenantId" trong JWT
   └─▶ TenantContext.set(tenantId)            // ThreadLocal
       └─▶ OrderService.getOrders() dùng TenantContext.get()
             └─▶ WHERE shop.id = :tenantId   // mọi query đều scope theo shop
   └─▶ finally { TenantContext.clear(); SecurityContextHolder.clearContext(); }
Đánh giá tốt: tenant id lấy từ JWT (không nhận từ request body/query), mọi truy vấn đều có điều kiện lọc tenant, và context luôn được giải phóng trong finally để không rò sang request kế tiếp trong cùng thread.

Luồng xử lý request

jwtInterceptor
  1. Gắn Authorization: Bearer <accessToken> từ sessionStorage
  2. Nhận lỗi 401 / 403 (trừ endpoint /auth/*)
  3. ▶ Gọi POST /auth/refresh   // shareReplay chống refresh đồng thời
  4. Retry request gốc 1 lần với token mới
  5. Nếu vẫn lỗi ▶ auth.logout() → chuyển hướng /auth/login

6 Điểm mạnh

Những điểm đã làm tốt, nên giữ nguyên khi refactor hoặc mở rộng.

✓ Cách ly multi-tenant đúng cách

Tenant id lấy từ JWT (không nhận từ client), mọi truy vấn đều scope theo shop, context giải phóng trong finally.

✓ Refresh token rotation

Token cũ bị xoá ngay khi dùng, chống replay. Có thêm cơ chế shareReplay ở FE chống refresh đồng thời.

✓ Chuẩn hoá response toàn hệ thống

ApiResponse<T> + PageResponse<T> + GlobalExceptionHandler trả đúng HTTP status, không lộ stack trace ra ngoài.

✓ Quản lý schema chuẩn

Flyway migration + ddl-auto: validate — không để Hibernate tự ý sửa bảng production.

✓ State machine rõ ràng

Chuyển trạng thái đơn hàng được định nghĩa tường minh ở cả backend và frontend, có xác thực chuyển hợp lệ.

✓ CI/CD hoàn chỉnh

Từ commit đến VPS tự động, có giới hạn tài nguyên cho máy yếu, tài liệu hướng dẫn chi tiết từng bước.

✓ Design system nhất quán

Dark theme "Apollo" tự viết, responsive đầy đủ, có export Excel thiết kế chuyên nghiệp.

✓ Đã chạy production thật

Đã deploy lên domain thật, đã có commit sửa CORS qua nginx — chứng tỏ pipeline hoạt động end-to-end.

7.1  Mức độ Cao — nên xử lý ngay

#01Production đang chạy profile dev → rò SQL và log nhạy cảm

docker-compose.prod.yml:32 đặt SPRING_PROFILES_ACTIVE: dev → kích hoạt jpa.show-sql: true và logging.level.com.saasoms: DEBUG trên production. Mọi câu SQL (chứa email, tên khách hàng) bị in ra log container.

→ Tạo application-prod.yml riêng, đổi thành SPRING_PROFILES_ACTIVE: prod, tắt show-sql và giảm log level.
#02Lỗi 403 "Access Denied" khiến người dùng bị đăng xuất oan

Trong jwt.interceptor.ts:47: const tryRefresh = (error.status === 401 || error.status === 403) && !req.url.includes("/auth/"). Nhân viên STAFF bấm xoá đơn → DELETE /api/orders/{id} có @PreAuthorize("hasRole('OWNER')") → Spring trả 403 → interceptor tưởng token hết hạn → gọi refresh → retry → vẫn 403 → catchError gọi auth.logout() → mất phiên đăng nhập. Mọi lỗi 403 hợp lệ đều dẫn tới đăng xuất ngoài ý muốn.

→ Chỉ refresh khi 401. Với 403 thì phân biệt AccessDenied (giữ nguyên, hiện toast lỗi) với token hết hạn.
#03Spring trả 403 thay vì 401 khi token hết hạn

SecurityConfig không cấu hình AuthenticationEntryPoint → ExceptionTranslationFilter với anonymous access trả về 403. Đó là nguyên nhân gốc buộc code phải "nghe" cả 403 (vấn đề #02).

→ Thêm .exceptionHandling(e -> e.authenticationEntryPoint((req, res, ex) -> res.sendError(401))) để trả 401 chuẩn khi thiếu/sai token.
#04CORS mở ở tầng nginx — reflect mọi origin

nginx.conf dùng add_header 'Access-Control-Allow-Origin' $http_origin always; kèm Access-Control-Allow-Credentials: true → phản chiếu bất kỳ origin nào và cho phép credentials. Kèm proxy_set_header Origin "" để Spring bỏ qua check CORS. Mọi website đều có thể gọi API của bạn.

→ Hardcode danh sách domain hợp lệ (app.darlynstore.com) thay vì reflect origin. Cân nhắc bỏ luôn Allow-Credentials vì token đặt trong header không dùng cookie.
#05.gitignore chặn *.md — tài liệu không được commit

Root .gitignore chứa dòng *.md → chặn mọi tài liệu Markdown mới (README, tài liệu API…). Hệ quả: frontend/CLAUDE.md và frontend/PROMPT_TEMPLATE.md hiện không được track trong git (chỉ setup-vps.md còn sót vì đã commit trước đó). File hướng dẫn cho AI và cho team không nằm trong repo.

→ Xoá *.md khỏi .gitignore, chỉ ignore .history/, node_modules/, dist/. Commit lại CLAUDE.md + PROMPT_TEMPLATE.md.
#06Mật khẩu tối thiểu chỉ 6 ký tự

RegisterRequest (@Size(min = 6)) và form đăng ký đều chỉ yêu cầu 6 ký tự — quá yếu cho một sản phẩm SaaS lưu trữ dữ liệu khách hàng và đơn hàng.

→ Tối thiểu 8 ký tự, yêu cầu độ phức tạp, chặn danh sách mật khẩu phổ biến, thêm rate-limit cho /auth/login.

7.2  Mức độ Trung bình

#07Module "Sản phẩm" chỉ là demo placeholder, không phải chức năng thật

product-list.component.ts là demo canvas pháo giấy hình tim với nội dung hardcode: name = "vợ yêu", message = "luôn xinh đẹp và yêu anh". Backend không hề có Product/Sku entity, controller, service — dù DB đã có sẵn bảng products và skus. Sidebar vẫn hiện mục "Sản phẩm" nên người dùng click vào sẽ thấy demo vui thay vì chức năng.

→ Xây module Products/Skills đầy đủ (entity, repository, service, controller) hoặc ẩn mục menu cho tới khi sẵn sàng.
#08Chưa có integration TikTok/Shopee — phần lõi giá trị sản phẩm chưa làm

Schema đã chuẩn bị đầy đủ: bảng platform_connections (access/refresh token), các cột platform_source, platform_order_id, external_id trên orders/products/customers, và SecurityConfig permit /webhooks/**. Nhưng không có controller/service nào dùng tới. Toàn bộ dữ liệu hiện là "Nhập tay".

→ Xây module platform_connections (mã hoá token), OAuth cho TikTok Shop / Shopee, webhook upsert đơn theo platform_order_id.
#09Dashboard sử dụng dữ liệu giả

barData và doughnutData hardcode mảng số; DASHBOARD_TOP_PRODUCTS là hằng tĩnh. Dropdown "Tuần trước / Tháng này / Quý này" không có tác dụng — biến selectedPeriod không được binding vào query. /api/orders/stats chỉ trả tổng toàn hệ thống, không lọc theo kỳ.

→ Bổ sung tham số date range cho /api/orders/stats, truyền selectedPeriod vào query, thay toàn bộ dữ liệu giả bằng dữ liệu thật.
#10Không có test nào cả

Backend có spring-boot-starter-test trong pom nhưng 0 file test (thư mục src/test không tồn tại). Frontend có 3 file .spec.ts là scaffold mặc định của ng generate, nhưng không cài test runner (không có karma/jest trong package.json) → không có lệnh npm test.

→ Bật test runner (Vitest hoặc Karma+Jasmine) cho FE; thêm unit test cho OrderService, AuthService; integration test với Testcontainers MySQL cho BE.
#11Tìm kiếm đơn hàng quá hẹp

OrderRepository.search chỉ match customer.fullName và CAST(o.id AS string). Không tìm theo SKU, tên sản phẩm hay số điện thoại. Dùng CAST nên không dùng được index → full scan khi bảng lớn.

→ Bỏ CAST, so khớp id bằng kiểu số; bổ sung tìm theo SKU / tên sản phẩm / SĐT với index phù hợp.
#12Memory leak trong ProductListComponent

startShow() dùng setInterval nhưng không lưu handle; ngOnDestroy chỉ disconnect() ResizeObserver, không clearInterval → timer chạy mãi, vẽ đè lên canvas đã bị huỷ.

→ Lưu interval id và clearInterval trong ngOnDestroy.
#13Tham số sort từ frontend bị backend bỏ qua

Frontend gửi sort=createdAt,desc nhưng backend hardcode Sort.by("createdAt").descending() → không thể sort theo cột khác (cũ nhất, giá trị đơn…).

→ Nhận sort từ query string, whitelist tên cột trước khi áp dụng.
#14Logic chuyển trạng thái lặp ở hai nơi

VALID_TRANSITIONS (backend) và ORDER_STATUS_TRANSITIONS (frontend) phải đồng bộ thủ công → dễ lệch khi thêm trạng thái mới, gây lỗi UX (hiện nút bấm không hợp lệ) hoặc lỗi API.

→ Trả danh sách trạng thái hợp lệ trong response của GET /api/orders/{id}, hoặc sinh cả hai từ một spec chung.
#15Refresh token hết hạn không được dọn dẹp

Không có scheduled job xoá token đã hết hạn → bảng refresh_tokens phình vô hạn theo thời gian.

→ Thêm @Scheduled job xoá token hết hạn hằng ngày, hoặc dọn rác ngay khi phát hiện hết hạn.
#16Không rate-limit / lockout đăng nhập, không audit log

/auth/login không có giới hạn số lần thử → dễ bị brute force. Đồng thời không ghi lại ai đã đổi trạng thái đơn hàng — rủi ro khi có tranh chấp nội bộ.

→ Thêm rate-limit (Bucket4j / filter), khóa tài khoản tạm thời sau N lần sai, và bảng audit log cho thao tác trạng thái đơn.
#17Export Excel giới hạn cứng 1.000 dòng

exportOrders() gọi getOrders({ size: 1000 }) một lần rồi nạp toàn bộ vào RAM trình duyệt và dựng workbook ExcelJS trong bộ nhớ. Dữ liệu lớn hơn sẽ bị cắt cụt mà không có cảnh báo.

→ Xây API export riêng phía server (streaming/cursor) hoặc export theo lô có phân trang.
#18JwtFilter cấp cả ROLE_USER cho mọi người dùng

Mọi token đều mang thêm authority ROLE_USER bất kể vai trò. Hiện chưa endpoint nào dùng hasRole('USER') nên chưa gây lỗi, nhưng rất dễ tạo lỗ hổng phân quyền khi mở rộng tính năng.

→ Chỉ cấp ROLE_<role> thực sự. Bỏ ROLE_USER hoặc định nghĩa rõ nó là role mặc định của STAFF.
#19SecurityUtils.getDetails() có thể ném ClassCastException

Ép kiểu thẳng (JwtDetails) auth.getDetails() mà không kiểm tra null/kiểu → nếu request không đi qua JwtFilter hoặc authentication là anonymous sẽ ném lỗi 500.

→ Kiểm tra instanceof JwtDetails và trả null/ném BusinessException.forbidden khi không hợp lệ.
#20Thiếu validation quan trọng ở CreateOrderRequest

Ba lỗ hổng validation: (1) items[].quantity không có @Min(1) → tạo được đơn có số lượng 0 hoặc âm; (2) discount không kiểm tra ≤ subtotal → tổng tiền có thể âm; (3) RegisterRequest.platform không whitelist → gán bất kỳ chuỗi nào vào cột VARCHAR(20).

→ Thêm @Min(1) cho quantity, validate discount ≤ subtotal ở tầng service, và whitelist giá trị platform.
#21OrderItem không map cột sku_id

Bảng order_items có sku_id + foreign key tới skus, nhưng entity không khai báo trường này → mất liên kết SKU, không thể trừ tồn kho, không tra cứu giá/variant chuẩn hoá.

→ Bổ sung trường skuId vào entity OrderItem và service tạo đơn.
#22orders.ordered_at luôn NULL

Cột tồn tại trong schema nhưng OrderService.createOrder() không set giá trị → trường thời gian đặt hàng không bao giờ có dữ liệu, vô dụng cho báo cáo.

→ Set orderedAt khi tạo đơn (mặc định LocalDateTime.now()).

8 Roadmap đề xuất

Kế hoạch 4 sprint, ưu tiên xử lý rủi ro bảo mật và hiện năng trước khi mở rộng tính năng.

SPRINT 1Ổn định & bảo mật1 tuần · ưu tiên cao
  1. Tạo profile prod, sửa docker-compose.prod.yml → tắt show-sql / DEBUG
  2. Sửa interceptor: chỉ refresh khi 401; thêm AuthenticationEntryPoint trả 401
  3. Whitelist CORS domain trong nginx.conf
  4. Xoá *.md khỏi .gitignore, commit CLAUDE.md + PROMPT_TEMPLATE.md
  5. Thêm @Min(1) cho quantity, validate discount ≤ subtotal, whitelist platform
  6. Nâng mật khẩu tối thiểu 8 ký tự
SPRINT 2Bổ sung chức năng lõi2–3 tuần
  1. Xây module Products / SKUs (entity, repository, service, controller) — dùng bảng products / skus đã có sẵn
  2. Nối skuId vào OrderItem, trừ tồn kho khi tạo đơn
  3. Bổ sung date range cho /api/orders/stats → dashboard bỏ dữ liệu giả
  4. Tìm kiếm đơn theo SKU / tên sản phẩm / SĐT, bỏ CAST(id AS string)
  5. Set orderedAt khi tạo đơn
SPRINT 3Tích hợp sàn TMĐT3–4 tuần
  1. Module platform_connections (mã hoá access/refresh token)
  2. OAuth TikTok Shop và Shopee
  3. Webhook /webhooks/tiktok, /webhooks/shopee → upsert đơn theo platform_order_id
  4. Đồng bộ sản phẩm & tồn kho từ sàn
SPRINT 4Chất lượng & vận hànhsong song
  1. Bật test runner FE (Vitest / Karma) + unit test cho OrderService, AuthService
  2. Integration test backend với Testcontainers MySQL
  3. Rate-limit đăng nhập, audit log, scheduled cleanup refresh token
  4. Tách tag version cho CI/CD + cơ chế rollback + cache Maven/npm
  5. Lazy-load ExcelJS / Chart.js, giảm initial bundle xuống dưới 512 kB

9 Hướng dẫn chạy dev

Lệnh để dựng lại môi trường phát triển cục bộ.

# Backend — cần MySQL ở :3306, database "saasoms"
cd D:\code\learn\SaaS\backend
mvn spring-boot:run
# → http://localhost:8080   ·   Swagger: /swagger-ui.html

# Frontend — proxy /api và /auth → :8080
cd D:\code\learn\SaaS\frontend
npm install && npm start
# → http://localhost:4200

Chạy full stack bằng Docker

cd D:\code\learn\SaaS
docker compose up -d
# MySQL :3307  ·  Backend :8080  ·  Frontend :4200
Lưu ý cấu hình: file backend/src/main/resources/application-dev.yml đã bị .gitignore loại trừ — cần copy từ application-dev.yml.example rồi điền thông tin MySQL. Nếu muốn chạy độc lập không cần MySQL, hãy dùng docker compose up để MySQL được dựng sẵn.

10 Kết luận

Đánh giá tổng thể và khuyến nghị hành động.

✔ Điểm đáng giữ

  • Nền tảng kỹ thu khá chắc: multi-tenant đúng, auth chuẩn, CI/CD hoàn chỉnh
  • UI đẹp, nhất quán, responsive, đã chạy trên production thật
  • Cấu trúc code sạch, phân tầng rõ, dễ tiếp tục phát triển

⚠ Điểm cần khắc phục

  • Profile dev đang chạy trên production — rò SQL/log
  • Logic 403 khiến người dùng bị logout oan
  • Hai module thương mại cốt lõi (Sản phẩm & tích hợp sàn) chưa được xây
  • Chưa có test nào, dashboard còn dùng dữ liệu giả
