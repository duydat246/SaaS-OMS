2 Kiến trúc Backend

Spring Boot 3.3.4 tổ chức theo module nghiệp vụ, hạ tầng dùng chung gói trong common/. Mô hình multi-tenant được áp dụng xuyên suốt từ tầng bảo mật xuống tầng repository.

Cơ chế cách ly multi-tenant

Luồng xác định tenant không bao giờ nhận giá trị từ client:

JWT (claim tenantId)
  → JwtFilter.set(SecurityContext, JwtDetails)
  → TenantContext.set(tenantId)   // ThreadLocal
  → OrderService đọc Long tenantId = TenantContext.get()
  → Repository query WHERE o.shop.id = :shopId

Đây là cách làm đúng: client không thể dùng IDOR để đọc dữ liệu của shop khác, vì mọi truy vấn đều gắn cứng shopId lấy từ token đã ký. TenantContext được clear() trong finally của filter để tránh rò rỉ sang request kế tiếp trong cùng thread.

State machine chuyển trạng thái đơn

PENDING   → CONFIRMED | CANCELLED
CONFIRMED → SHIPPED   | CANCELLED
SHIPPED   → DELIVERED | CANCELLED
DELIVERED → (kết thúc)
CANCELLED → (kết thúc)

Bảng transition khai báo tường minh trong OrderService.java:34-40, mọi chuyển tiếp không hợp lệ bị từ chối bằng BusinessException.badRequest. Đây là thiết kế tốt — trạng thái được kiểm ở tầng service chứ không phải ở controller.

Lớp phản hồi & xử lý lỗi

ApiResponse<T>

{ success, data, message } — @JsonInclude(NON_NULL) nên message bị ẩn khi null. Tất cả controller đều trả về wrapper này, frontend map theo r.data.

PageResponse<T>

{ content[], meta: { page, size, totalElements, totalPages } } — bọc trực tiếp Page của Spring Data.

GlobalExceptionHandler

5 handler: BusinessException (theo status), MethodArgumentNotValidException (gộp message field), BadCredentialsException, AccessDeniedException, và fallback 500.

BusinessException

Factory helpers conflict / forbidden / badRequest / notFound giúp mã lỗi nhất quán và trả HTTP status đúng (409, 403, 400, 404).

4 Kiến trúc Frontend

Angular 18 hoàn toàn standalone — không có NgModule, không có thư viện quản lý state bên ngoài; trạng thái đi qua Angular signals và RxJS.

Luồng xử lý request

Component (signal / Observable)
  → Service (HttpClient + HttpParams)
  → jwtInterceptor
      1. gắn header Authorization: Bearer <accessToken>
      2. lỗi 401/403 & URL khác /auth → POST /auth/refresh
      3. retry request gốc 1 lần với token mới
      4. refresh thất bại → logout + chuyển về /auth/login
  → Backend

Interceptor được đăng ký qua provideHttpClient(withInterceptors([jwtInterceptor])). Cơ chế shareReplay(1) + biến refreshInFlight$ trong AuthService chống gọi refresh song song khi nhiều request cùng gặp 401.

Auth & phiên làm việc

  • AuthService giữ currentUser (signal), isLoggedIn và isOwner (computed).
  • Session lưu trong sessionStorage — không phải localStorage. (Tài liệu CLAUDE.md đang ghi sai, xem #25.)
  • authGuard bảo vệ toàn bộ route dưới shell layout; /auth/** nằm ngoài guard.

Cấu trúc routing

/auth/**            → lazy  (không guard)
/                   → ShellComponent  (authGuard)
  ├── /dashboard       → lazy
  ├── /orders          → lazy
  │     ├── /orders/new    → OrderFormComponent
  │     └── /orders/:id    → OrderDetailComponent  (id nhận qua @Input)

withComponentInputBinding() cho phép OrderDetailComponent nhận @Input() id trực tiếp từ tham số route. TopbarComponent tự dựng pageTitle từ URL qua setTitleFromUrl() — cần cập nhật hàm này mỗi khi thêm route mới.

Điểm UI

  • Layout "Apollo": sidebar + topbar, CSS class apollo-layout, hỗ trợ thu gọn sidebar và overlay điều hướng trên mobile (ShellLayoutService).
  • Bảng dữ liệu dùng p-table lazy + paginator, có custom paginator cho dashboard (1 … 2 3 4 … 10).
  • Biểu đồ dùng ChartModule (Chart.js): bar doanh thu/lợi nhuận + doughnut theo nhóm hàng.
  • Export Excel bằng exceljs (ExcelExportService).
  • Chuẩn PrimeNG: [style] nhận object, [severity] của p-tag phải đúng union 'success'|'info'|'secondary'|'contrast'|'warning'|'danger'.

5 Hạ tầng & Triển khai

Docker Compose cho cả dev lẫn prod, CI/CD tự động build và đẩy lên VPS qua SSH, Cloudflare Tunnel làm lớp trước (edge) thay cho expose trực tiếp.

docker-compose.yml (dev)

  • MySQL mysql:8.0 — port 3307 (tránh đụng MySQL local), volume mysqldata, healthcheck mysqladmin ping
  • Backend build từ ./backend — port 8080, profile dev
  • Frontend build từ ./frontend — port 4200
  • Backend depends_on: mysql (service_healthy)

docker-compose.prod.yml

  • Dùng image từ Docker Hub (${DOCKERHUB_USERNAME}/saasoms-*), không build tại VPS
  • Giới hạn RAM: MySQL 256M, JVM 320M (-Xmx256m), nginx 32M
  • MySQL tune: buffer pool 128M, max-connections 50, tắt performance-schema, skip-name-resolve
  • Network riêng saasoms-net — chỉ nginx publish ra ngoài (port 80)
  • Secrets lấy từ .env trên VPS

nginx.conf — reverse proxy

Proxy /api/ và /auth/ → http://backend:8080, phần còn lại là SPA fallback try_files $uri $uri/ /index.html. Vì frontend và API cùng origin qua nginx, CORS không cần thiết — nhưng cấu hình hiện tại lại bật CORS theo kiểu reflect Origin (xem #01).

CI/CD — .github/workflows/deploy.yml

push (main | dev)
  → checkout
  → docker login (DOCKERHUB_USERNAME / DOCKERHUB_TOKEN)
  → build & push saasoms-backend:latest

      cd /var/www/saasoms

6 Điểm mạnh

Nền tảng kiến trúc và vận hành khá tốt so với mức độ trưởng thành của dự án — phần lớn rủi ro nằm ở cấu hình triển khai và các tính năng chưa hoàn thiện, không phải ở thiết kế nền tảng.

✓ Cách ly multi-tenant chặt chẽ

Tenant lấy từ JWT đã ký, không bao giờ từ client; mọi query đều gắn shop.id. Loại bỏ hoàn toàn lớp lỗi IDOR.

✓ Refresh token rotation

Token cũ bị xoá khi refresh, bị thu hồi khi logout. Cơ chế quay vòng token đúng chuẩn, giảm rủi ro replay token.

✓ State machine đơn hàng

Bảng transition khai báo tường minh, validate ở tầng service, có hỗ trợ chuyển sang CANCELLED từ mọi trạng thái trung gian.

✓ Schema có versioning

Flyway migration V1__init_schema.sql — deploy không lo mất dữ liệu, thêm bảng sau này bằng V2__.

✓ Docker image nhỏ & an toàn cho VPS 1GB

Multi-stage build (alpine), memory limit cho từng container, healthcheck MySQL, swap 2GB — thiết kế đúng bài toán hạ tầng thực tế.

✓ Tài liệu vận hành đầy đủ

setup-vps.md bao phủ từ tạo token, khai báo secrets đến xử lý sự cố — giảm rào cản cho người triển khai mới.

✓ Hợp đồng API nhất quán

ApiResponse / PageResponse thống nhất hai đầu, có OpenAPI tự sinh, frontend map theo r.data xuyên suốt.

✓ Frontend hiện đại & nhất quán về signal

Standalone components, lazy routes, shareReplay chống refresh trùng, takeUntilDestroyed thay cho manual unsubscribe.

7 Vấn đề phát hiện

34 phát hiện đã được đối chiếu trực tiếp với mã nguồn. Phân loại theo mức độ ảnh hưởng: Cao = lỗ hổng bảo mật / sự cố chắc chắn xảy ra · Trung bình = sai lệch chức năng / rủi ro vận hành · Thấp = nợ kỹ thuật, cải thiện chất lượng.

7.1  Mức độ Cao — cần xử lý ngay (P0)

#01nginx phản chiếu Origin không kiểm tra allowlist — mọi website đều gọi được API kèm credentials

Cấu hình dùng add_header 'Access-Control-Allow-Origin' $http_origin always — biến Origin của request thành giá trị trả về, không đối chiếu danh sách cho phép. Kết hợp Access-Control-Allow-Credentials: true, bất kỳ website nào cũng có thể gọi API bằng cookie/credential của người dùng.

nginx.conf:10, 25, 35, 46

Cách sửa: App và API đã cùng origin qua nginx nên bỏ hẳn khối CORS trong nginx.conf (kể cả block OPTIONS), đồng thời xoá proxy_set_header Origin "" — cả hai đều là hack lách CORS của Spring và không còn cần thiết.
#02Production đang chạy profile dev — bật show-sql, log toàn bộ SQL và log file

SPRING_PROFILES_ACTIVE: dev trong compose prod kích hoạt application-dev.yml với spring.jpa.show-sql: true và log level com.saasoms: DEBUG. Trên VPS, mọi câu SQL (kèm dữ liệu khách hàng) đều bị in ra stdout → rò rỉ dữ liệu và nghẽn I/O.

docker-compose.prod.yml:33 · application-dev.yml:8,12

Cách sửa: Tạo application-prod.yml (show-sql: false, log level INFO), đổi compose prod sang SPRING_PROFILES_ACTIVE=prod.
#03shippingFee / discount / unitPrice thiếu @NotNull → NullPointerException trả về HTTP 500

Các field có default BigDecimal.ZERO khi khong được gửi, nhưng nếu client gửi tường minh "shippingFee": null thì Jackson ghi đè giá trị null → subtotal.add(req.getShippingFee()) ném NPE. Tương tự unitPrice bị null sẽ làm multiply(null) lỗi.

CreateOrderRequest.java · OrderService.java:89, 103-105

Cách sửa: Thêm @NotNull cho shippingFee, discount, unitPrice (kèm @PositiveOrZero sẵn có).
#04quantity không giới hạn dương → tạo đơn với số lượng âm làm tổng tiền âm

OrderItemRequest.quantity là int mặc định 1 nhưng không có @Positive. Gửi quantity: -5 với unitPrice: 100000 sẽ tạo totalPrice = -500000, kéo subtotal và totalAmount âm — thao túng số liệu doanh thu.

CreateOrderRequest.OrderItemRequest · OrderService.java:88-101

Cách sửa: @Positive(message = "Quantity must be at least 1") và kiểm tra totalAmount >= 0 trước khi lưu.
#05Feature "Sản phẩm" là trang demo vẽ pháo hoa Canvas — không phải chức năng quản lý sản phẩm

Toàn bộ features/products/ không liên quan gì tới sản phẩm: ProductListComponent vẽ pháo hoa hình trái tim bằng Canvas với dòng chữ name = "vợ yêu", message = "luôn xinh đẹp và yêu anh". ProductFormComponent và ProductDetailComponent là component rỗng (template 3 dòng). Backend hoàn toàn không có module products/skus dù DB đã có bảng.

Sidebar đang dẫn người dùng tới menu "Sản phẩm" giả, và commit d575a8c feat: add feature products gây hiểu nhầm về trạng thái tính năng.

features/products/** · modules/ (thiếu product) · sidebar.component.ts:58

Cách sửa: Ẩn menu "Sản phẩm" cho tới khi có API thật; viết backend module products + skus trước rồi mới làm lại UI.
#06.gitignore chứa *.md — mọi tài liệu Markdown đều không được commit

Quy tắc *.md ở thư mục gốc chặn toàn bộ file Markdown ở mọi cấp. Hệ quả quan sát được: frontend/CLAUDE.md và frontend/PROMPT_TEMPLATE.md bị ignore dù đã tạo và dùng; tài liệu API / README mới cũng sẽ biến mất khi commit.

.gitignore:7

Cách sửa: Xoá dòng *.md, thay bằng danh sách cụ thể (.history/, .claude/, skills-lock.json); sau đó git add -f cho các file md đáng giữ.
#07Swagger UI và /api-docs mở công khai ở production

permitAll() cho /swagger-ui/**, /api-docs/** giúp dev nhưng ở production làm lộ toàn bộ API contract, mô hình dữ liệu và các endpoint quản trị — giúp kẻ tấn công lập bản đồ API.

SecurityConfig.java:44

Cách sửa: Tách danh sách whitelist theo profile — chỉ cho phép ở dev, ở prod chặn hoặc bảo vệ bằng role.
#08Secrets mặc định nằm trong mã nguồn

JWT_SECRET có sẵn giá trị cố định dev-secret-key-must-be-at-least-32-chars-long; mật khẩu MySQL dev/dev và root/123456 nằm trong compose và application-dev.yml. Nếu biến môi trường không được override, production sẽ chạy bằng secret mặc định.

docker-compose.yml:26-29 · application-dev.yml:5

Cách sửa: Bỏ giá trị default khỏi mã nguồn (bắt buộc truyền qua env), tách application-prod.yml không chứa secret, dùng .env (đã có trong .gitignore).
#09Không rate-limit cho /auth/login — dễ bị brute force mật khẩu

Endpoint login không có giới hạn số lần thử, không có khóa tài khoản tạm thời, không có delay tăng dần. application-dev.yml còn bật show-sql nên mọi lần thử sai đều để lại dấu vết trong log — thuận tiện cho việc dò mật khẩu.

AuthController.java:31 · AuthService.java:63-77

Cách sửa: Thêm rate-limit theo IP/email (Bucket4j hoặc filter đếm số lần), khóa tạm thời sau N lần thất bại, ghi log audit các lần thử.

7.2  Mức độ Trung bình — nên xử lý trong sprint tới (P1)

#10Dashboard dùng số liệu giả cho toàn bộ biểu đồ

Bar chart (doanh thu/lợi nhuận theo T2–CN) và doughnut (Điện tử/Thời trang/Gia dụng) đều là mảng số hardcode trong component. Bộ lọc selectedPeriod / DASHBOARD_PERIOD_OPTIONS không có tác dụng — đổi lựa chọn không làm gì. Người dùng dễ tưởng đây là số liệu thật.

dashboard.component.ts:113-179

Cách sửa: Thêm API GET /api/orders/stats?from&to trả dữ liệu theo kỳ và theo nhóm hàng, thay toàn bộ số liệu giả.
#11Không có test tự động nào — backend không có src/test, frontend chỉ có spec rỗng, CI không chạy test

Ba file spec frontend là template mặc định do CLI sinh ra (chỉ assert title). Backend hoàn toàn không có thư mục test dù pom.xml đã khai báo spring-boot-starter-test và spring-security-test. Workflow CI chỉ build Docker image, không chạy test — mọi hồi quy lên production đều không bị chặn.

backend/src/test (không tồn tại) · frontend/**/*.spec.ts · deploy.yml

Cách sửa: Ưu tiên test cho các luồng rủi ro cao: tenant isolation (user A không đọc được data shop B), state machine chuyển trạng thái, refresh token rotation, interceptor 401/403. Thêm bước mvn test + npm test vào CI trước khi build image.
#12setInterval không được huỷ trong ProductListComponent → memory leak

startShow() gọi setInterval(() => this.createFirework(), 500) nhưng ngOnDestroy() chỉ disconnect() ResizeObserver, không clearInterval. Mỗi lần vào lại route là thêm một interval sống mãi, mỗi tick lại sinh thêm particle — bộ nhớ và CPU tăng dần. requestAnimationFrame cũng không được huỷ.

product-list.component.ts:148-149, 80-82

Cách sửa: Lưu id interval và frame id vào field, clearInterval() + cancelAnimationFrame() trong ngOnDestroy. (Kèm #05 — trang này nên bị gỡ bỏ.)
#13Spring trả 403 thay vì 401 khi token thiếu/hết hạn

Không cấu hình AuthenticationEntryPoint nên request không có token tới endpoint yêu cầu xác thực nhận 403 (AccessDenied) thay vì 401 (Unauthorized) — sai ngữ nghĩa HTTP và làm client khó phân biệt "chưa đăng nhập" với "không đủ quyền". Frontend hiện phải bắt cả 401 lẫn 403 mới kịp refresh.

SecurityConfig.java:36-51 · jwt.interceptor.ts:33-35

Cách sửa: Thêm bean AuthenticationEntryPoint trả 401 với body ApiResponse thống nhất; phân biệt rõ 401 (chưa xác thực) và 403 (đã xác thực nhưng thiếu quyền).
#14generateSlug có race condition khi hai shop trùng tên đăng ký đồng thời

Vòng lặp while (shopRepository.existsBySlug(slug)) rồi save — hai request đồng thời cùng tên shop đều thấy slug chưa tồn tại, cùng insert, một trong hai vi phạm unique constraint và nhận HTTP 500 thay vì lỗi business thân thiện.

AuthService.java:125-138

Cách sửa: Bắt DataIntegrityViolationException để trả 409, hoặc sinh slug có hậu tố ngẫu nhiên (nanoID) để không cần kiểm tra vòng lặp.
#15Tham số size phân trang không được giới hạn

GET /api/orders?size=1000000 được Spring chấp nhận và tải toàn bộ bảng vào RAM rồi map sang DTO — rủi ro DoS và OOM trên VPS 1GB (JVM chỉ có 256MB heap).

OrderController.java:35

Cách sửa: Validate size trong khoảng 1–100, hoặc dùng Pageable với @Max(100) / setMaxPageSize().
#16Export Excel giới hạn cứng 1000 dòng, không cảnh báo khi bị cắt

Dashboard gọi getOrders({ page: 0, size: 1000 }) rồi xuất Excel. Với shop có hơn 1000 đơn, file xuất ra bị thiếu dữ liệu mà người dùng không hề được báo.

dashboard.component.ts:322

Cách sửa: Thêm endpoint export chuyên biệt stream dữ liệu, hoặc phân trang vòng lặp và ghi báo "đã xuất N/M đơn" khi vượt giới hạn.
#17Tìm kiếm đơn hàng quá hẹp — chỉ khớp tên khách hàng hoặc mã đơn

Query chỉ có LOWER(o.customer.fullName) LIKE ... hoặc CAST(o.id AS string) LIKE .... Không tìm được theo số điện thoại, mã đơn sàn, hay tên sản phẩm trong đơn — ba nhu cầu tra cứu phổ biến nhất khi xử lý đơn hàng.

OrderRepository.java:22-34

Cách sửa: Bổ sung o.customer.phone, o.platformOrderId và EXISTS trên order_items.productName.
#18Tham số sort gửi từ frontend bị backend bỏ qua

Frontend luôn gửi sort=createdAt,desc nhưng controller không khai báo tham số sort và luôn cố định Sort.by("createdAt").descending(). Hiện tại vô hại vì giá trị trùng khớp, nhưng giao diện "sắp xếp theo cột" sẽ không bao giờ hoạt động.

order.service.ts:23 · OrderController.java:36

Cách sửa: Nhận sort và whitelist các trường được phép sắp xếp (chống sort injection), hoặc bỏ gửi tham số thừa.
#19Chính sách mật khẩu quá yếu — tối thiểu 6 ký tự, không có kiểm tra độ mạnh

RegisterRequest chỉ yêu cầu @Size(min = 6), không có yêu cầu hoa/thường/số/ký tự đặc biệt, không chặn mật khẩu phổ biến. Đây là điểm vào đầu tiên của brute force (#09).

RegisterRequest.java

Cách sửa: Nâng tối thiểu lên 8–10 ký tự, kiểm tra độ mạnh, và thêm giới hạn độ dài tối đa (chống DoS qua BCrypt với chuỗi cực dài).
#20CI/CD deploy cả main lẫn dev ra cùng một VPS, không có môi trường staging

Workflow trigger trên cả hai nhánh đều dẫn tới cùng lệnh SSH triển khai. Một lần push nhầm lên dev cũng lên production. Không có bước kiểm tra sau deploy, không có rollback.

deploy.yml:5, 33-47

Cách sửa: dev chỉ build + chạy test; chỉ main mới deploy. Thêm bước healthcheck sau up -d và script rollback về tag image trước.
#21Image tag :latest — không rollback được và không truy vết được phiên bản

Cả hai image đều gắn :latest. Khi deploy lỗi không có image phiên bản cũ để quay lại, và không xác định được server đang chạy mã nguồn nào.

deploy.yml:24, 31

Cách sửa: Gắn tag theo commit SHA (:${{ github.sha }} hoặc :v1.2.3), giữ tag latest làm alias trỏ tới bản mới nhất.
#22Container chạy với quyền root và không có .dockerignore

Cả backend (JRE) và frontend (nginx) đều chạy root. Thêm nữa, frontend/Dockerfile dùng COPY . . mà không có .dockerignore → có thể đóng gói node_modules, dist, .angular, .history vào build context, làm build chậm và image nặng.

backend/Dockerfile · frontend/Dockerfile

Cách sửa: Thêm user không phảm root trong cả hai image, thêm .dockerignore cho từng app (node_modules, dist, .angular, .history, .git).
#23orders.ordered_at không bao giờ được ghi → trường luôn null

Cột ordered_at TIMESTAMP NULL tồn tại trong schema và được trả về trong OrderResponse, nhưng OrderService.createOrder() không gọi setOrderedAt(...) — mọi đơn đều có orderedAt = null, kể cả đơn mới tạo.

Order.java:69 · OrderService.java:107-116 · OrderResponse.java:25,65

Cách sửa: Set orderedAt = LocalDateTime.now() khi tạo đơn (hoặc dùng @CreationTimestamp nếu bỏ cột khỏi migration).
#24Chưa có tích hợp TikTok/Shopee dù schema đã sẵn sàng

Bảng platform_connections (token, refresh token, thời hạn, unique theo tenant+platform) đã được thiết kế đầy đủ nhưng không có entity hay service nào dùng tới. Các cột platform_source / platform_order_id / external_id trên orders, products, customers cũng đang để trống — hệ thống hiện chỉ quản lý đơn nhập tay.

V1__init_schema.sql:126-139

Cách sửa: Xem đây là hướng mở rộng chính của sản phẩm: viết module platform đọc/ghi platform_connections, rồi thêm job đồng bộ đơn hàng theo lịch.
#25Tài liệu CLAUDE.md lệch với mã nguồn

Tài liệu ghi session lưu ở localStorage nhưng code dùng sessionStorage; mục "Routing structure" không liệt kê route /products đã tồn tại; mục "Order status" mô tả TagSeverity nên định nghĩa ở một chỗ nhưng thực tế khai báo 3 nơi (xem #26). Tài liệu sai dẫn tới agent sửa nhầm hướng.

frontend/CLAUDE.md:34, 36-44, 64

Cách sửa: Cập nhật CLAUDE.md cho khớp code thực tế (và nhớ commit file này sau khi sửa #06).

#26Kiểu TagSeverity bị khai báo lặp 3 lần

Cùng một union 'success'|'info'|'secondary'|'contrast'|'warning'|'danger' xuất hiện ở dashboard.component.ts:48, order-list.component.ts:26, order-detail.component.ts:19 — trong khi CLAUDE.md lại nói nên định nghĩa tại một chỗ.

3 component trong features/orders và features/dashboard

Cách sửa: Export TagSeverity từ features/orders/constants/order.constants.ts (nơi đã có ORDER_STATUS_SEVERITY) rồi import ở mọi nơi.
#27Phong cách component không nhất quán — inline template 290 dòng và constructor DI xen kẽ inject()

OrderListComponent nhét toàn bộ template + styles vào decorator (~290 dòng) trong khi các component khác tách file .html/.scss. Về DI: ShellComponent và TopbarComponent dùng constructor injection còn phần lớn code còn lại dùng inject() — trong khi PROMPT_TEMPLATE.md quy định "Prefer inject() over constructor DI".

order-list.component.ts:48-292 · shell.component.ts:44-53 · topbar.component.ts:76-84

Cách sửa: Tách template của OrderListComponent ra file riêng; chuẩn hoá về inject() toàn bộ.
#28Bảng refresh_tokens không có index hạn dùng và không có job dọn dẹp

Token hết hạn vẫn nằm trong bảng vô thời hạn; truy vấn findByToken dựa vào unique index của cột token nên không chậm, nhưng bảng phình dần theo số phiên đăng nhập và tốn dung lượng VPS.

V1__init_schema.sql:27-34

Cách sửa: Thêm index expires_at và một scheduled job xoá token đã hết hạn (hoặc xoá theo lô trong lúc refresh).
#29JwtFilter được Spring Boot đăng ký thêm một lần ngoài security chain

JwtFilter là @Component extends OncePerRequestFilter nên Boot tự đăng ký nó vào servlet chain ở LOWEST_PRECEDENCE, song song với vị trí đã khai trong SecurityConfig. OncePerRequestFilter chặn lần chạy thứ hai trong cùng request, nhưng vì attribute bị xoá khi lần đầu kết thúc, filter thực tế vẫn chạy 2 lần → JWT được parse 2 lần cho mọi request.

JwtFilter.java:22 · SecurityConfig.java:48

Cách sửa: Đăng ký FilterRegistrationBean với setEnabled(false) để vô hiệu hoá bản đăng ký tự động, hoặc bỏ @Component và khai báo @Bean trong SecurityConfig.
#30Refresh token rotation gây mất session khi hai tab refresh đồng thời

Luồng refresh xoá token cũ rồi cấp token mới. Nếu hai tab cùng refresh một lúc, tab thứ hai dùng token đã bị xoá → nhận "Invalid refresh token" → logout, dù tab thứ nhất vẫn hoạt động bình thường.

AuthService.java:80-93

Cách sửa: Cho phép tái sử dụng token cũ trong một khoảng ngắn (grace period) hoặc dùng mô hình refresh token family với cơ chế phát hiện tái sử dụng.
#31order_items không ghi sku_id / sku_code dù schema đã có

Schema có sku_id (FK skus) và sku_code, nhưng khi tạo đơn, OrderItem chỉ lưu productName / variant dạng text tự do. Không thể thống kê doanh thu theo SKU, theo tồn kho, hay trừ kho khi bán.

OrderService.java:88-97

Cách sửa: Cho phép truyền skuId khi tạo đơn và validate thuộc tenant; đồng thời bổ sung cơ chế trừ tồn kho.
#32Ô tìm kiếm ở topbar không gắn handler — UI chết

Thanh tìm kiếm trong topbar chỉ là input trang trí, không có model, không có sự kiện, không dẫn tới kết quả nào. Người dùng có thể gõ và tưởng đang tìm kiếm.

topbar.component.ts:43-49

Cách sửa: Nối vào tìm kiếm đơn hàng (điều hướng tới /orders?search=...) hoặc bỏ hẳn cho tới khi có chức năng tra cứu toàn cục.
#33Thiếu lớp Entity / DTO / Service / Repository cho products và skus

Ba bảng products, skus, platform_connections đã có trong migration nhưng không có bất kỳ class Java nào tương ứng — nghĩa là phần lớn giá trị thiết kế dữ liệu của dự án chưa được khai thác.

backend/src/main/java/com/saasoms/modules/

Cách sửa: Xem #05 và #24 — đây là hai đầu việc lớn tiếp theo.
#34Không có audit log cho thao tác nhạy cảm

Không ghi lại ai đã đổi trạng thái đơn, ai đã đăng nhập, ai đã hủy đơn. Khi có khiếu nại về đơn hàng thì không có dữ liệu để đối chiếu — đặc biệt quan trọng với hệ thống xử lý tiền thật.

toàn bộ modules/

9 Hướng dẫn chạy dev

Yêu cầu: JDK 21, Maven 3.9+, Node 20+, Docker (tuỳ chọn).

Chạy bằng Docker Compose (đơn giản nhất)

# toàn bộ stack: mysql:3307 · backend:8080 · frontend:4200
docker compose up -d

# theo dõi log
docker compose logs -f backend

# dừng (giữ dữ liệu trong volume mysqldata)
docker compose down

Chạy tách biệt để debug

# Backend — cần MySQL sẵn có ở localhost:3306
cd backend
mvn spring-boot:run
# mặc định profile dev: root/123456 @ localhost:3306/saasoms

# Frontend — dev server + proxy
cd frontend
npm install
npm start
# http://localhost:4200, proxy /api và /auth → localhost:8080

Lưu ý proxy dev: proxy.conf.js chỉ proxy /auth với method POST; các request GET /auth/* bị bypass về /index.html để không bị backend trả lỗi 500 — vì /auth/login và /auth/register còn là route Angular ở màn hình đăng nhập/đăng ký.

Build production

# backend
cd backend && mvn package -DskipTests
# → target/saas-oms-0.0.1-SNAPSHOT.jar

# frontend
cd frontend && npm run build
# → dist/saas-oms-frontend/browser

Tài liệu API

http://localhost:8080/swagger-ui.html   # giao diện Swagger
http://localhost:8080/api-docs        # định dạng OpenAPI JSON

Tài khoản mẫu

Chưa có seed dữ liệu. Tạo tài khoản qua POST /auth/register (tự sinh shop + user OWNER), hoặc đăng ký trực tiếp trên giao diện tại /auth/register.

10 Kết luận

Dự án có nền tảng kiến trúc tốt và đã đi tới mức triển khai production thực tế — vấn đề không nằm ở thiết kế mà nằm ở các cấu hình chưa được siết lại và những tính năng đang ở trạng thái demo.

Đánh giá tổng thể

Backend — chắc chắn về mặt kiến trúc

  • Tenant isolation + JWT rotation + state machine đều đúng cách làm
  • Phân tầng rõ ràng, entity/DTO/service tách biệt
  • Điểm cần gấp: cấu hình prod, validation đầu vào, endpoint quản trị

Frontend — chất lượng tốt, có dữ liệu giả

  • Signal-first, lazy routes, interceptor xử lý refresh chuẩn
  • PrimeNG dùng đúng chuẩn, layout responsive có mobile nav
  • Điểm cần gấp: feature "Sản phẩm" là demo, dashboard dùng số giả

DevOps — chạy được nhưng chưa an toàn

  • CI/CD + tài liệu VPS rất đầy đủ
  • Điểm cần gấp: CORS mở, profile dev ở prod, tag :latest, chưa có test

Sản phẩm — còn thiếu phần lõi

  • Đơn hàng thủ công: hoàn chỉnh
  • Thiếu: sản phẩm/SKU, khách hàng, tồn kho, đồng bộ sàn TMĐT
  • Schema đã chuẩn bị sẵn cho các phần này

Ba việc cần làm ngay hôm nay

  1. Bỏ CORS trong nginx.conf — đây là lỗ hổng thực sự đang mở trên production, sửa trong 5 phút.
  2. Đổi profile production sang prod và tạo application-prod.yml — đang log toàn bộ SQL ra ngoài.
